# Presenter: native macOS recording research

Research date: **2026-10-16**. Local evidence: **macOS 27.0.1 (26A434)** and **macOS SDK 27.0**, with Command Line Tools selected. This note distinguishes documented API behavior from local validation results recorded below.

## Recommended implementation

1. Build a camera-only preview using AVFoundation in a nonactivating `NSPanel`.
2. Open Apple's Screenshot app with `NSWorkspace`; let the user choose a whole display or selected portion, microphone, and save location.
3. Keep camera session configuration and start/stop calls on one serial execution context, with AppKit presentation on the main actor.
4. Verify that the saved `.mov` contains the moving webcam preview and microphone audio before calling the combined workflow validated.

This keeps movie encoding and microphone capture in Apple's recorder. It needs no custom video compositor or independent camera movie file. **Inference:** selecting one app window can omit the separate webcam panel; use a whole display or a selected region containing both the content and panel for this workflow.

## Apple recorder and launch route

**Verified Apple documentation:** Screenshot records the entire screen or a selected portion. On Tahoe 26 and later, it also supports selected-window recording. Its Options menu selects the microphone and save location. The user starts recording in Apple's toolbar and stops using the menu-bar Stop control or Command-Control-Escape. Automatic output uses a `.mov` filename. QuickTime's File → New Screen Recording can open this same Screenshot interface. The article was published September 17, 2026. [Apple: record the screen on Mac](https://support.apple.com/en-au/102618).

**Verified public API:** `NSWorkspace.urlForApplication(withBundleIdentifier:)` resolves an app, and `openApplication(at:configuration:completionHandler:)` launches it and reports a launch result. [NSWorkspace](https://developer.apple.com/documentation/appkit/nsworkspace).

**Verified locally:** `/System/Applications/Utilities/Screenshot.app/Contents/Info.plist` declares `com.apple.screenshot.launcher`. `/System/Library/CoreServices/screencaptureui.app/Contents/Info.plist` declares `com.apple.screencaptureui`. These identifiers are installation evidence, not an Apple promise that a specific recorder mode will be selected. Prefer the user-facing Screenshot launcher; resolve through `NSWorkspace`, handle a missing URL or launch error, and offer the documented Shift-Command-5 instruction as a fallback. Confirm launching and relaunching behavior on the target machine.

**Verified local QuickTime scripting contract:** `/System/Applications/QuickTime Player.app/Contents/Resources/QuickTimePlayerX.sdef`, lines 80–82, exposes `new screen recording` (`MVWRnscr`). Unlike `new movie recording` and `new audio recording`, it declares no returned recording document. Therefore, do not assume its result can be passed to `start` or `stop`. The dictionary alone does not guarantee programmatic screen-recording lifecycle control on modern macOS. AppleScript also introduces an Automation authorization path that a simple app launch avoids. No coordinate automation is needed for the proposed design.

**Unresolved:** No public, documented callback for the Screenshot app's recording start, stop, cancellation, or final output URL was identified in this research. Presenter should describe its action as “Open Screen Recorder” and must not claim that opening the toolbar means a recording has begun.

## Camera preview and recording inclusion

**Verified:** `AVCaptureVideoPreviewLayer` is a Core Animation layer that displays a live camera feed from an `AVCaptureSession`. Apple documents styling it as another `CALayer` and states that a preview requires no capture output. A camera input plus preview is enough; a separate `AVCaptureMovieFileOutput` is unnecessary. [Preview layer](https://developer.apple.com/documentation/avfoundation/avcapturevideopreviewlayer), [capture-session setup](https://developer.apple.com/documentation/avfoundation/setting-up-a-capture-session), [Apple AVFoundation guide: video preview](https://developer.apple.com/library/archive/documentation/AudioVideo/Conceptual/AVFoundationPG/Articles/04_MediaCapture.html).

**Empirical requirement:** Those references do not promise that every capture backend includes live `AVCaptureVideoPreviewLayer` contents. Record and play a short clip, with visible camera motion, to rule out a black or frozen webcam region. A still screenshot proves less than video playback. The local baseline movie passed this check; other capture backends, devices, and Space transitions remain unqualified. Cutout uses `AVCaptureVideoDataOutput` because Vision needs camera frames for segmentation.

## Session threading and Swift 6

**Verified:** `startRunning()` synchronously waits for the session to start or fail. Apple recommends a serial queue to keep the main queue responsive. Apple's current camera-service examples also use an actor to own capture operations. [AVCaptureSession](https://developer.apple.com/documentation/avfoundation/avcapturesession), [startRunning](https://developer.apple.com/documentation/avfoundation/avcapturesession/startrunning()), [Apple camera-service actor example](https://developer.apple.com/documentation/DockKit/controlling-a-dockkit-accessory-using-your-camera-app).

**Verified local SDK:** `AVCaptureSession.h`, lines 460–478 and 580–598, requires `commitConfiguration()` before `startRunning()` or `stopRunning()`; violating this ordering throws `NSGenericException`. Both lifecycle calls block. Use one serial owner for creation, input replacement, configuration, start, and stop. Keep configuration transactions synchronous and balanced. Do not independently dispatch start and configuration onto unrelated queues.

**Implementation recommendation, not an Apple mandate:** For a small Swift 6 AppKit app, a dedicated serial-queue camera controller is sufficient. An actor with a serial executor is also valid, but unnecessary unless it simplifies the design. Any `@unchecked Sendable` bridge must document the exact queue confinement it promises; the annotation itself does not make `AVCaptureSession` thread-safe. Keep UI state changes on the main actor. Compile with the actual Swift 6 concurrency checks to verify the chosen boundary.

## Camera discovery

**Verified local SDK:** `AVCaptureDevice.h` declares `.builtInWideAngleCamera` on macOS 10.15+, and `.external` and `.continuityCamera` on macOS 14+. Its Continuity Camera discussion at lines 643–653 says that `NSCameraUseContinuityCameraDeviceType = true` opts into the distinct Continuity Camera device type. Without that key, those cameras report the built-in wide-angle type. `.externalUnknown` is deprecated in favor of `.external` on macOS 14. [Continuity Camera device type](https://developer.apple.com/documentation/avfoundation/avcapturedevice/devicetype-swift.struct/continuitycamera), [external device type](https://developer.apple.com/documentation/avfoundation/avcapturedevice/devicetype-swift.struct/external).

For a macOS 14+ target, discover `[.builtInWideAngleCamera, .external, .continuityCamera]` for `.video`, position `.unspecified`, and include the Continuity key. Persist a camera's `uniqueID`; fall back to an available default if it disappears. Handle an empty device list and connect/disconnect events. Continuity Camera availability still depends on the user's devices and system configuration. [Apple: Continuity Camera integration](https://developer.apple.com/videos/play/wwdc2022/10018/).

## Permissions and ownership

**Verified:** macOS grants camera and microphone permission separately per app. Presenter requires `NSCameraUsageDescription`, must check `.video` authorization before configuring capture, and should request access when the user invokes the preview. Denied and restricted states need an actionable camera-unavailable message. [Apple: media authorization on macOS](https://developer.apple.com/documentation/bundleresources/requesting-authorization-for-media-capture-on-macos).

**Architecture inference:** If Presenter only creates a video input, it should request camera permission only. Selecting a microphone in Screenshot is Apple's recorder's action; asking for Presenter microphone access would not authorize another process. Presenter also need not request Screen Recording access if it never captures screen pixels itself. Actual macOS prompt wording and responsible-process attribution for Screenshot/QuickTime must be observed rather than assumed. A sandboxed or hardened build must additionally use the relevant camera capability. [Apple: capture authorization and macOS entitlements](https://developer.apple.com/documentation/avfoundation/requesting-authorization-to-capture-and-save-media).

## Overlay across Spaces and full-screen apps

**Verified API semantics:** `.canJoinAllSpaces` allows a window in every Space. `.canJoinAllApplications` permits eligible windows to join other apps' sets and full-screen Spaces. `.primary`, `.auxiliary`, and `.canJoinAllApplications` are mutually exclusive. `.fullScreenPrimary`, `.fullScreenAuxiliary`, and `.fullScreenNone` are another mutually exclusive group. [Window collection behavior](https://developer.apple.com/documentation/appkit/nswindow/collectionbehavior-swift.struct). The local `NSWindow.h` confirms these restrictions.

**Apple staff-tested guidance, not a universal guarantee:** A May 2026 Apple DTS answer recommends accessory activation, `NSPanel` with `.nonactivatingPanel`, `hidesOnDeactivate = false`, `.screenSaver` level, and `[.canJoinAllSpaces, .canJoinAllApplications, .fullScreenAuxiliary, .stationary]`. DTS reports success above Safari, QuickTime, and YouTube full screen on macOS 26. [Apple Developer Forums: floating overlay](https://developer.apple.com/forums/thread/826308).

Use a floating nonactivating panel for the normal case and verify whether `.screenSaver` level is needed on this machine. High window levels can interfere with Apple's capture toolbar, so test recorder selection, menu access, dragging, and hiding the overlay. Verify full-screen behavior on macOS 27, multiple displays, Stage Manager, and switching Spaces. Do not promise appearance over protected or system-controlled surfaces.

## Required empirical acceptance check

1. Grant Presenter camera access and confirm the selected camera displays moving video.
2. Open Screenshot from Presenter and select a full display or region containing the overlay.
3. Select a microphone and an explicit local save destination in Screenshot Options.
4. Record visible webcam movement while speaking for several seconds.
5. Stop with Apple's menu-bar control or Command-Control-Escape.
6. Open the saved `.mov` and confirm simultaneous screen content, moving webcam image, and audible speech.
7. Relaunch Presenter and confirm camera choice, shape, size, mirroring, and position persist.
8. Repeat with a full-screen app and a Space transition to qualify the overlay claim.

The local desktop recording and settings-relaunch checks passed. The full-screen and Space-transition checks remain open. See the local validation evidence at the end of this document.

## Live person cutout: clarified requirement, 2026-10-16

The user confirmed the baseline screen, camera, and speech recording works, then clarified that the desired overlay isolates the person's silhouette with a transparent background. Circle and rounded crops do not satisfy that requirement. The smallest native extension is **Vision person segmentation → Core Image alpha composite → transparent AppKit layer**, while Screenshot continues to encode the screen and microphone.

**Verified availability:** `VNGeneratePersonSegmentationRequest` is available on **macOS 12+**, so it supports this app's macOS 14 target. The newer Swift `GeneratePersonSegmentationRequest` requires **macOS 15+**. The installed SDK 27 confirms both declarations. The original request's `supportedOutputPixelFormats()` helper also requires macOS 15, although its `outputPixelFormat` property and supported one-component formats predate that helper. Use the original request across the current target rather than maintaining two implementations. [Original request](https://developer.apple.com/documentation/vision/vngeneratepersonsegmentationrequest), [new Swift request](https://developer.apple.com/documentation/vision/generatepersonsegmentationrequest).

**Verified matte behavior:** The request returns a `VNPixelBufferObservation`. Set `.balanced` and `kCVPixelFormatType_OneComponent8` for live video. Eight-bit single-channel output is the default; half-float and float masks are also supported. The local `VNGeneratePersonSegmentationRequest.h` says `.accurate` adds matting refinement to balanced output and the request may retain previous masks for temporal stability. Reuse one request for a continuous camera stream, and recreate it after camera changes or a new cutout session. [Output format](https://developer.apple.com/documentation/vision/vngeneratepersonsegmentationrequest/outputpixelformat), [quality levels](https://developer.apple.com/documentation/vision/vngeneratepersonsegmentationrequest/qualitylevel-swift.enum).

Apple's live-video sample chooses balanced quality, applies the same orientation to Vision and the source `CIImage`, then scales the lower-resolution mask independently in X and Y to match the oriented source extent. Its `.right` orientation is for the sample's iPhone camera; it is **not** a universal webcam setting. Use upright `.up` for an upright Mac buffer, and verify the built-in, external, and Continuity cameras rather than inferring orientation from the preview layer. Normalize image origins before scaling the mask if orientation produces a nonzero extent. Apply mirroring once to the completed person composite, or to its display layer, so source and matte remain aligned. [Apple's matte sample](https://developer.apple.com/documentation/vision/applying-matte-effects-to-people-in-images-and-video), [Vision orientation parameter](https://developer.apple.com/documentation/vision/vnimagerequesthandler/init(cmsamplebuffer:orientation:options:)-335k4).

**Verified compositing:** `CIBlendWithMask` uses grayscale zero for the background and one for the foreground. Set the camera image as `inputImage`, the scaled mask as `maskImage`, and a clear image cropped to the source extent as `backgroundImage`; crop the result to that extent. This creates alpha transparency. A one-component matte contains intensity, so use `blendWithMask()` or the sample's `blendWithRedMask()`, rather than assuming `blendWithAlphaMask()` reads its intensity. The filter itself dates to OS X 10.4. Apple explicitly describes an empty background image as producing transparency. [Core Image filter reference](https://developer.apple.com/library/archive/documentation/GraphicsImaging/Reference/CoreImageFilterReference/), [Apple: lift subjects](https://developer.apple.com/videos/play/wwdc2023/10176/).

Recommended integration with the existing sources:

1. Add `Cutout` to `OverlayShape`; retain the current preview layer for Circle and Rounded.
2. Add a small `NSObject` conforming to `AVCaptureVideoDataOutputSampleBufferDelegate` that owns a reusable Vision request and `CIContext` on a dedicated serial processing queue.
3. Add/remove one `AVCaptureVideoDataOutput` on `CameraCapture`'s existing serial session queue when entering/leaving Cutout. Set `alwaysDiscardsLateVideoFrames = true` and process synchronously in the delegate rather than starting an unbounded task for each frame.
4. Render the alpha composite to a `CGImage` off the main actor, preferably at the overlay's backing-pixel dimensions. Deliver only the latest completed image to the main actor and reject images from an earlier camera/mode generation.
5. Add a separate layer for the cutout in `CameraPreviewView`; use clear background, no geometric border, no corner crop, and disabled implicit animations. The existing panel is already nonopaque and clear. Its rectangular frame can remain draggable even where its visual pixels are transparent.
6. On hide, camera replacement, or shutdown, disable delivery, detach the output delegate, drain/reset its serial state safely, and clear stale layer contents. On Vision failure, show a useful error and keep the cutout clear; do not silently reveal the raw camera background. An empty person mask should display an empty cutout.

**Verified performance constraints:** Apple's TN2445 recommends discarding late frames and warns that retaining capture buffers or processing too slowly can stall other outputs, including preview. Use an autorelease pool per processed frame and bounded UI delivery. Prefer a supported uncompressed bi-planar `420f`/`420v` format, with a supported fallback, instead of forcing BGRA for every camera; Apple's TN3121 explains BGRA's conversion and memory cost. The available formats change with the device's active format. The installed SDK marks `automaticallyConfiguresOutputBufferDimensions` and `deliversPreviewSizedOutputBuffers` **unavailable on macOS**. [Frame drops](https://developer.apple.com/library/archive/technotes/tn2445/_index.html), [pixel format choice](https://developer.apple.com/documentation/technotes/tn3121-selecting-a-pixel-format-for-an-avcapturevideodataoutput).

Reuse `CIContext(options: [.cacheIntermediates: false])`; the SDK says this selects the default Metal device. Explicit `CIContext(mtlDevice:options:)` is available on macOS 10.11+. Apple recommends reusing contexts and direct Metal rendering for demanding video. For this small overlay, `CALayer.contents = CGImage` is a simpler initial design, **not a verified throughput claim**. If measurement shows high CPU use or lag, first reduce cutout processing cadence/resolution; consider `MTKView` only if needed. [Core Image performance](https://developer.apple.com/library/archive/documentation/GraphicsImaging/Conceptual/CoreImaging/ci_performance/ci_performance.html), [video pipeline guidance](https://developer.apple.com/videos/play/wwdc2020/10008/).

**Acceptance remains empirical:** Check hair/hand edges, no-person frames, moving hands, both mirror settings, camera changes, hide/show, and mode changes. Verify no camera background rectangle in the live overlay or saved screen recording, and confirm screen content shows through the removed background. A normal Screenshot `.mov` records the already-composited display; it does not need an alpha-bearing movie codec. This workflow needs neither external model packages nor a replacement screen encoder.

## Distribution release: researched 2026-10-16

**Deferred scope:** The user chose a simple source-based GitHub installation instead of prebuilt executable distribution. The signing, universal-binary, and notarization sequence below is future reference, not a requirement for the current local-build installer.

The deployment target is **macOS 14 or later**. The installer builds for the host processor. Local runtime testing covers Apple silicon on macOS 27.0.1; Intel and macOS 14 runtime compatibility remain untested. A local executable or ad hoc signature does not establish that an ordinary downloaded binary passes Gatekeeper.

**Verified release requirements:** Sign the final app with a **Developer ID Application** identity, enable **Hardened Runtime**, include a **secure timestamp**, omit `get-task-allow`, and obtain accepted notarization. Apple Development, Mac App Distribution, ad hoc, and local certificates do not replace Developer ID for this direct-distribution path. [Apple notarization requirements](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution), [distribution signing](https://developer.apple.com/documentation/xcode/creating-distribution-signed-code-for-the-mac/).

The camera-only Presenter process needs `com.apple.security.device.camera = true` in the signed entitlements and `NSCameraUsageDescription` in `Info.plist`. Hardened Runtime and App Sandbox are separate capabilities; direct distribution does not require adding App Sandbox. Preserve the existing ownership boundary: Screenshot captures microphone/screen content, so Presenter does not need microphone or Apple Events entitlements for its current implementation. Retest camera access after enabling Hardened Runtime. [Hardened Runtime](https://developer.apple.com/documentation/security/hardened-runtime), [camera entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.device.camera).

**Verified tooling here:** Apple Swift **6.4**, SDK **27.0**, and selected Command Line Tools expose `notarytool` and `stapler`. `swift build --help` supports `--triple`, `--scratch-path`, `--configuration release`, and `--show-bin-path`; it does not advertise the older `--arch` recipe. `swiftc -print-target-info` accepts both `arm64-apple-macosx14.0` and `x86_64-apple-macosx14.0`, and the SDK includes both Vision module interfaces. This verifies available compiler targets, **not a successful build or run of each Presenter architecture**. [SwiftPM build command](https://github.com/swiftlang/swift-package-manager/blob/main/Sources/PackageManagerDocs/Documentation.docc/SwiftBuild.md).

Recommended release sequence:

1. Build release executables for each target triple with separate scratch directories, retaining macOS 14 as both the package minimum and deployment target. Read each output directory with the same options plus `--show-bin-path`.
2. Merge the executables with `xcrun lipo -create ... -o ...` before signing. Verify both slices with `lipo -archs`, inspect minimum OS load commands, and inspect linked libraries for development-machine paths. The final `.app` must contain all required resources and any non-system runtime dependencies. [Apple: universal binaries](https://developer.apple.com/documentation/apple-silicon/building-a-universal-macos-binary).
3. Finalize the app's identifier, versions, privacy strings, icon/resources, and executable mode. Sign nested code inside-out if present, then sign the app with the verified options `--sign`, `--force`, `--timestamp`, `--options runtime`, and `--entitlements`. Do not modify sealed bundle files afterward. Avoid using `--deep` as a substitute for correctly signing nested code. [Apple: distribution signing](https://developer.apple.com/documentation/xcode/creating-distribution-signed-code-for-the-mac/).
4. Verify the signature with `codesign --verify --deep --strict --verbose=2 Presenter.app`, then inspect its identity, runtime flags, timestamp, and camera entitlement. The verification use of `--deep` is distinct from using it to sign.
5. Create a ZIP using Apple's documented `ditto -c -k --keepParent Presenter.app Presenter.zip`. Submit the archive with `xcrun notarytool submit Presenter.zip --keychain-profile PROFILE --wait`, using a user-configured Keychain profile. Preserve the submission ID, require status `Accepted`, and retrieve/review its log, including warnings. A successful upload alone is insufficient. [Apple: custom notarization workflow](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow).
6. Staple the accepted ticket to **Presenter.app**, validate it with `xcrun stapler validate Presenter.app`, then recreate the final ZIP from the stapled app. ZIP archives cannot themselves be stapled. Submit/staple only when the user has authorized the Apple upload; no credentials need to be embedded in scripts. [Apple: stapling and ZIP delivery](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow).
7. Run `syspolicy_check distribution Presenter.app` on macOS 14+. Test the final ZIP through an actual quarantining browser download on a clean Mac or VM, install it as a user would, and verify launch, camera permission, cutout, screen recording, speech, save, and relaunch. Also test first launch without networking to verify stapling. Repeat the functional tests on native Intel and Apple silicon and on the minimum supported OS. Notarization is necessary but does not prove Gatekeeper or runtime compatibility. [Apple: packaging and distribution tests](https://developer.apple.com/documentation/xcode/packaging-mac-software-for-distribution), [Apple DTS: notarized apps can still fail Gatekeeper](https://developer.apple.com/forums/thread/814949).
8. Publish the exact tested archive with a versioned filename, support requirements, installation instructions, and SHA-256 checksum. Hosting/publication is a separate action; this research neither uploads nor publishes a release.

**Container choice:** ZIP is sufficient and keeps this app's release workflow small. A DMG is also supported: sign the app and DMG, notarize the outermost container, and staple its ticket. A Developer ID Installer identity is for installer packages, not for signing the app. On this macOS 27 host, `hdiutil create -help` now reports that image creation is deprecated in favor of `diskutil image create`; verify that command's help before implementing a DMG workflow. Avoid copying an old unverified image-creation recipe. [Apple packaging guidance](https://developer.apple.com/documentation/xcode/packaging-mac-software-for-distribution), [Developer ID certificate types](https://developer.apple.com/help/glossary/developer-id-certificate/).

**Account boundary:** Developer ID certificates are issued through Apple Developer Program/Enterprise Program membership. A usable local signing identity includes its associated private key; a downloaded public `.cer` alone is insufficient. If no eligible identity or notarization credentials are configured, a universal runnable development artifact can still be produced, but the ordinary public-download release remains blocked on the publisher's signing/notarization setup. Do not describe an unsigned/ad hoc build as notarized or ask users to disable Gatekeeper as an installation prerequisite. Certificate/account setup belongs to the owner; no private keys or passwords were read for this research. [Apple: Developer ID certificates](https://developer.apple.com/help/account/certificates/create-developer-id-certificates/), [Apple: code-signing identities](https://developer.apple.com/library/archive/documentation/Security/Conceptual/CodeSigningGuide/Procedures/Procedures.html).

**Offline distinction:** Timestamping, submission, and stapling require Apple services during release preparation. A properly stapled app can pass its first notarization check offline, subject to the Mac's normal security policy. Presenter can then perform its local camera/cutout workflow without a server. That is a product requirement to test, not evidence of a completed signed release. [Apple DTS: stapling](https://developer.apple.com/forums/thread/720093), [Apple: secure timestamps](https://developer.apple.com/documentation/technotes/tn3161-inside-code-signing-certificates).

## Local validation evidence, 2026-10-16

- All 12 tests passed outside the workspace sandbox: eight placement cases and four Core Image person-mask cases. The sandbox rendered even an unfiltered Core Image control as zero pixels; running the same tests in the normal macOS environment resolved that environment limitation.
- The release app compiled and its ad-hoc signature passed strict verification. No Developer ID identity is installed; Gatekeeper rejected the ad-hoc artifact for direct distribution. The source-based installer does not promise a trusted prebuilt download.
- The user confirmed a baseline recording contains screen movement, camera movement, and speech. Metadata showed 1920 × 1080 video and 48 kHz stereo audio beginning together.
- The user confirmed a separate Cutout recording works. Its approximately 14-second movie contains 1920 × 1080 video and 48 kHz stereo audio. A decoded frame showed a waving person over the desktop, with the camera background removed.
- Cutout style, camera choice, mirroring, size, and position persisted across a quit/relaunch. Live camera capture resumed and ended on quit.
- The optional QuickTime AppleScript compiled outside the workspace sandbox. Its complete scripted recording workflow remains untested.
- Physical display/device changes, Intel hardware, the macOS 14 minimum, full-screen app combinations, and Space transitions remain open empirical checks.

Source installation guidance was checked against [Apple's Command Line Tools guide](https://developer.apple.com/documentation/xcode/installing-the-command-line-tools), [Swift's macOS installation guide](https://www.swift.org/install/macos/), and [GitHub's cloning guide](https://docs.github.com/en/repositories/creating-and-managing-repositories/cloning-a-repository). The repository has no package dependencies to download during the build.

## Native panel design: researched 2026-10-17

Apple positions Liquid Glass in the functional layer for controls and navigation. Standard components adopt the platform treatment and adapt to system appearance and accessibility settings. The Presenter panel therefore keeps its system popover surface, native controls, semantic text styles, and a single prominent recorder action. Adding separate glass backgrounds to every settings group would add unnecessary layers. [Materials](https://developer.apple.com/design/human-interface-guidelines/materials), [adopting Liquid Glass](https://developer.apple.com/documentation/technologyoverviews/adopting-liquid-glass), [custom SwiftUI glass](https://developer.apple.com/documentation/SwiftUI/Applying-Liquid-Glass-to-custom-views).

The installed SDK declares `.glassProminent` available on macOS 26 and later. The implementation also guards its use with Swift 6.2 or later so older supported Swift 6 toolchains can use the existing prominent-button style. The macOS 14 deployment target remains unchanged. Local compilation used Swift 6.4 and SDK 27; older-toolchain and minimum-OS runtime checks remain unverified.
